# 迅雷容器空闲上传排查

排查日期：2026-11-11。

后续已在封装程序中加入 `XL_UPLOAD_LIMIT`，可直接限制容器总出站流量，使用方式见 [README](../README.md#上传限速)。下文记录加入功能前的排查证据。

用户反馈：`latest` 和 V4 均出现没有下载任务时持续上传，有时占满上行带宽。本次核对了仓库源码、镜像仓库的实际镜像内容，以及两个版本使用的官方迅雷程序；没有访问发生问题的部署主机。

## 当前判断

首要疑点是迅雷官方内核的 P2P 后台共享及其上传策略。两份内核都有上传管理器、上传监控和上传开关调用，封装程序没有提供独立的上传限速或关闭共享参数。下载不限速时，所核对的内核也向下载库传入不限制上传的参数，具备占满上行的条件。

目前不能把所有空闲上传都定性为 P2P，也不能断言默认策略一定会在空闲时上传。还需要用部署端的日志和连接计数区分内核共享、额外插件、文件传输，以及下载期间的确认报文。静态检查没有发现本仓库自行实现持续上传的代码。

## 源码与内核证据

### 封装程序没有控制上传

- `Dockerfile` 启动 `/xlp`；V4 在 `xlp.go` 的准备阶段下载套件，然后运行 `xunlei-pan-cli-launcher`。
- `spk/url.go` 的网络请求是获取官方套件的 HTTP GET。它发生在初始化阶段，不是持续发送下载文件的实现。
- `config.go` 没有上传速度或关闭 P2P 的配置项。
- `xlp.go` 把 `XL_PREVENT_UPDATE` 转换为启动器的 `-update_url` 参数；此参数不能控制 P2P 上传或插件上传。
- `docker-compose.yaml` 的桥接网络和面板端口映射没有限制容器主动外连。减少映射端口也不能禁止已有外连上的上传。

### 两份官方内核都有实际上传调用

通过 ELF 动态符号和 Go 函数表恢复函数地址，并反汇编核对调用关系，找到了：

```text
pkg/download_runner.uploadWatcher
  → download.SetUploadSwitch
  → C 下载库的 set_upload_switch
  → XLSetUploadSwitch
```

这不只是未使用的字符串。`3.21.0` 的上传监控在 `0x14f4cba` 调用 `download.SetUploadSwitch`，`3.23.5` 对应调用在 `0x16d4248`。下载库还包含 `P2PUploadAcceptor`、`UploadManager`、`UploadSpeedController` 等上传模块。

两份内核的策略分支都能识别 `always`、`disable`、`disabled`、`downloading`：

- `always` 允许上传，不能由“面板没有下载任务”推导出关闭。
- `disable`、`disabled` 走关闭分支。
- 空策略和 `downloading` 依赖内核自己的 `DownloadRunning` 状态。
- 未识别的非空策略走允许上传的分支。
- 另外有文件可用性等关闭条件，最终开关也受这些条件影响。

`3.23.5` 的内嵌群晖平台配置中，`upload_strategy` 为 `downloading`。因此不能声称该套件的默认策略就是 `always`；部署端最终生效的策略及内部状态仍需查日志。

### 上传限速随下载限速设置

两份内核的 `pkg/download_runner.registerRunners.func3` 都调用 `download.SetSpeed`。机器指令显示：

```text
下载限速 L > 0：传入 SetSpeed(L, 整数除法 L/10)
下载限速 L <= 0：传入 SetSpeed(L, -1)
```

对应调用地址为 `3.21.0` 的 `0x14ee120` 和 `3.23.5` 的 `0x16cc180`。`SetSpeed` 随后调用 C 下载库的 `set_speed`，下载库提供 `XLSetSpeedLimit` 和上传速度控制器。

这说明上传限速并非独立配置。内核传入的限速值能否约束所有实际流量，还取决于下载库执行结果和流量来源，尤其不能保证约束独立插件。

### 已有同类反馈

上游议题 [#104：有什么办法可以限制其上传吗？](https://github.com/cnk3x/xunlei/issues/104) 明确报告“没有开网心云的插件，但上传却占用满了”，后续用户也报告上传和磁盘负载问题。这支持把内核共享列为首要排查方向，但社区反馈不能替代具体部署的连接证据。

## 部署端如何确认

以下命令在实际 Docker 宿主机执行，把 `xunlei` 替换为容器名。不会修改网络规则。

```sh
# 核对容器和内嵌套件版本；内核自动更新后，还需结合进程确认。
docker inspect --format '{{.Config.Image}} {{.Image}} {{.HostConfig.NetworkMode}}' xunlei
docker exec xunlei cat /xunlei/var/packages/pan-xunlei-com/target/bin/bin/version
docker top xunlei -eo pid,ppid,comm

# 连续观察网络计数；网络输入、输出显示的是累计值，需要比较增量。
docker stats xunlei

# 使用宿主机的工具检查容器网络；不要求镜像内安装工具。
xl_container_pid=$(docker inspect --format '{{.State.Pid}}' xunlei)
sudo nsenter -t "$xl_container_pid" -n ss -tinp
sudo nsenter -t "$xl_container_pid" -n ss -uanp

# 限时查看连接头信息，兼顾短连接和 UDP；宿主机需安装抓包工具。
sudo nsenter -t "$xl_container_pid" -n timeout 20s tcpdump -i any -nn -q -s 96 -c 300
```

在上行异常时，间隔十秒运行两次 TCP 检查，比较同一连接的 `bytes_sent` 增量，同时看关联进程：

| 证据 | 含义 |
| --- | --- |
| `xunlei-pan-cli` 连接的发送字节持续增加 | 流量来自官方内核；结合上传监控日志确认共享状态 |
| 其他插件进程持续发送 | 排查对应插件；关闭内核 P2P 不一定影响插件 |
| 外部客户端连接面板端口并大量接收 | 排查面板文件传输；面板默认没有密码认证 |
| 下载流量很大，但发出的主要是确认报文 | 上行可能来自下载协议开销，需要与持续发送数据区分 |

必要时在部署配置中开启 `XL_DEBUG=true` 后重建容器，在异常发生时检查近期日志中的 `uploadWatcher`、`UploadStrategy`、`DownloadRunning`、`SetUploadSwitch` 和 `GetUploadInfo`。关注最终策略、内部下载状态以及开关设置是否返回错误。调试日志可能包含登录信息、令牌和文件名，分享前需脱敏。

在允许短暂停止服务的时段，对比停止容器前后的上行增量，可以确认异常是否由该容器产生；这只能定位到容器，不能单独区分 P2P 和插件。

## 处理方向

1. 优先确认发送进程和最终上传策略。如果是插件，停用对应插件后复测。
2. 如果确认是内核共享，检查实际版本是否提供关闭共享的设置。二进制存在内部 `upload_strategy` 字段，不代表本项目已经提供稳定可用的配置入口；不要直接修改保存登录状态的文件或套用未经验证的接口。
3. 可在面板中设置下载限速，验证上述上传限速绑定是否生效。此方法同时降低下载速度，也不能保证限制插件流量。
4. 要可靠保护上行带宽，在独立桥接网络中对容器出站流量使用路由器策略或 `tc` 限速，并覆盖 TCP、UDP 和 IPv6。容器内使用 `tc` 通常需要 `iproute2`、`NET_ADMIN` 及宿主机内核支持；主机网络模式共享宿主机网络，不能直接对公共网卡套用容器限速命令。

目前没有实测依据证明升级 V4、开启 `XL_PREVENT_UPDATE`、减少端口映射或只封禁 UDP 能彻底解决此问题。
